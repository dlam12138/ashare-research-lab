# Agent Working Agreement

## 1. Purpose

本文件约束所有参与本项目的开发 Agent。

项目目标是构建一个本地运行、免费数据优先、可解释、可复现的A股研究平台，核心模块只有两个：

1. 个股价值评估；
2. 市场机制验证。

所有开发工作都必须能够明确服务于上述至少一个模块。

---

## 2. Project Boundaries

当前项目不做：

- 自动买卖和券商下单；
- 明日涨跌预测；
- 精确目标价预测；
- 黑箱式买卖评分；
- LLM直接替代统计计算；
- 新闻情绪自动荐股；
- 全市场长期分钟级数据仓库；
- 深度学习价格预测；
- 与核心目标无关的大而全功能。

如果新增功能不能明确服务于价值评估或机制验证，应暂停实施，并在记录中说明原因。

---

## 3. Required Workflow

每次接到任务后必须按以下顺序工作：

1. 阅读项目现有文档和相关代码；
2. 检查 `agent/agent.md`；
3. 查看 `agent/record/` 中最近的工作记录；
4. 明确本次任务的目标、范围和禁止修改项；
5. 检查当前Git状态；
6. 制定最小可行实施计划；
7. 先建立或更新本次工作记录；
8. 再修改代码；
9. 执行测试和静态检查；
10. 检查最终差异；
11. 更新工作记录中的结果、验证和遗留问题；
12. 汇报实际完成内容，不得把计划描述成已经完成。

---

## 4. Record-First Rule

任何会修改项目文件的任务，都必须在 `agent/record/` 中建立一份记录。

推荐命名格式：

```text
YYYY-MM-DD_HHMM_简短任务名.md
```

例如：

```text
2026-07-27_1430_initialize-data-layer.md
```

如果无法可靠获得当前时间，可以使用：

```text
YYYY-MM-DD_序号_简短任务名.md
```

例如：

```text
2026-07-27_01_initialize-data-layer.md
```

同一任务应持续更新同一份记录，不要为每个小命令建立新文件。

---

## 5. Record Content Requirements

每份工作记录至少包含：

```markdown
# 工作记录：任务名称

## 基本信息

- 日期：
- Agent：
- 当前分支：
- 开始提交：
- 任务来源：
- 对应模块：价值评估 / 机制验证 / 数据底座 / 工程治理

## 任务目标

说明本次任务要解决什么问题。

## 范围

本次允许修改的文件和模块。

## 非目标

明确本次不处理的内容，防止任务扩张。

## 开始前状态

- 当前Git状态；
- 已存在的相关实现；
- 已发现的风险；
- 依赖和环境情况。

## 实施计划

列出准备执行的步骤。

## 决策记录

只记录可审查的工程决策，不记录私密或冗长的内部思维过程。

每项决策包含：

- 决策内容；
- 采用原因；
- 考虑过的替代方案；
- 未采用替代方案的原因；
- 潜在风险。

## 实际操作

按执行顺序记录：

1. 查看了什么；
2. 修改了什么；
3. 新增了什么；
4. 删除了什么；
5. 执行了哪些命令；
6. 每一步得到什么结果。

不要伪造未执行的命令或测试。

## 数据与方法说明

涉及数据研究时必须记录：

- 数据来源；
- 接口或文件；
- 下载时间；
- 数据日期范围；
- 复权方式；
- 单位；
- 缺失值处理；
- 财报公告日期处理；
- 是否可能存在未来数据泄漏；
- 使用的统计假设和阈值。

## 验证

记录实际执行的检查，例如：

```text
pytest
ruff check
git diff --check
特定数据一致性检查
样例报告生成
手工抽查
```

每项标明：

- 命令；
- 是否通过；
- 关键输出；
- 未通过原因。

## 结果

说明：

- 已完成内容；
- 未完成内容；
- 与原计划的差异；
- 当前是否可用；
- 是否存在条件通过。

## 遗留问题

列出尚未处理的问题，不要为了让记录看起来完整而隐藏失败。

## 下一步建议

只写与当前项目核心目标直接相关的下一步。

## 最终文件变更

列出新增、修改、删除的文件。

## 最终Git状态

记录：

- 当前分支；
- 当前提交；
- 是否存在未提交修改；
- 是否创建提交或Tag；
- 是否执行推送。
```

---

## 6. Honesty and Evidence

Agent必须遵守：

- 没有查看过的文件，不能说已经查看；
- 没有运行的测试，不能说已经通过；
- 没有生成的结果，不能写成已完成；
- 不确定的内容必须明确标为假设；
- 统计相关性不能表述为因果关系；
- 公开行情只能支持到何种证据等级，就写到何种程度；
- 失败、警告和条件通过必须保留；
- 不得为了得到预期结论而修改阈值、样本期或排除日期；
- 修改研究条件时，必须在记录中说明修改时间和原因。

---

## 7. Data Principles

所有数据实现必须遵守：

- 免费数据优先；
- 数据源可替换；
- 原始数据尽量保留；
- DuckDB和Parquet作为默认本地存储；
- 记录数据来源和抓取时间；
- 财务数据按实际公告日期生效；
- 禁止未来数据泄漏；
- 明确区分前复权、不复权和后复权；
- 明确成交量、成交额、价格和财务字段的单位；
- 对关键数据进行跨来源抽查；
- 数据缺失不能自动视为零；
- 接口失败不能静默返回空结果；
- 免费网页接口不应成为不可替换的唯一依赖。

---

## 8. Research Principles

### 价值评估

必须分别展示：

- 企业质量；
- 估值吸引力；
- 价值兑现能力；
- 风险水平；
- 风险否决项。

不得只使用一个综合分掩盖严重风险。

### 机制验证

必须包含：

- 可计算的假设；
- 样本期；
- 条件阈值；
- 市场代理；
- 控制变量；
- 描述性统计；
- 替代解释；
- 稳健性检验；
- 支持证据；
- 反证证据；
- 证据等级。

不得把"与护盘行为特征一致"写成"证明有人护盘"。

---

## 9. Engineering Principles

- 优先最小、可验证的改动；
- 不随意重构无关代码；
- 不同时引入多个大型框架；
- 不复制已有功能；
- 公共逻辑应有单一入口；
- 数据提供方应通过统一接口适配；
- 失败必须返回明确错误；
- 文件写入尽量采用原子方式；
- 关键计算应有单元测试；
- 统计结果应可由固定输入重复生成；
- 报告必须显示数据截止日期和参数；
- 不提交缓存、密钥、大型原始数据和私人文件；
- 未经明确要求不得执行推送、发布或删除远程资源。

---

## 10. Git Rules

开始前执行并记录：

```text
git status --short
git branch --show-current
git rev-parse --short HEAD
```

完成后至少执行并记录：

```text
git diff --check
git status --short
git diff --stat
```

除非任务明确要求：

- 不自动推送；
- 不强制推送；
- 不重写已有提交；
- 不删除已有Tag；
- 不提交密钥、模型、缓存和大型数据文件；
- 不把无关修改混入本次任务。

如果工作区开始时已有用户修改，必须保护这些修改，不能覆盖或擅自清理。

---

## 11. Completion Standard

只有满足以下条件，才能宣称任务完成：

- 目标范围内的实现已落地；
- 工作记录已更新；
- 测试或验证已实际执行；
- 失败和警告已明确记录；
- 最终差异已检查；
- 没有把计划冒充结果；
- 没有引入明显未来数据泄漏；
- 没有偏离价值评估或机制验证的项目目标。

若部分条件未满足，应使用：

```text
未完成
部分完成
条件通过
```

而不是写"全部完成"。

---

## 12. Final Response Format

每次任务结束时，Agent的回复至少包括：

1. 实际完成了什么；
2. 修改了哪些文件；
3. 执行了哪些验证；
4. 验证结果；
5. 工作记录文件路径；
6. 未解决问题；
7. Git状态；
8. 是否提交、是否推送。

回复应简洁、具体、可核验。

## Claude Code Entry Point

Claude Code 通过项目根目录的 `CLAUDE.md` 自动加载本规范。

根目录 `CLAUDE.md` 必须包含：

```text
@agent/agent.md
```

每次新会话开始时，Claude Code 应：

1. 确认 `CLAUDE.md` 和本文件已经进入当前上下文；
2. 阅读 `agent/record/README.md`；
3. 阅读最近三份记录；
4. 阅读与当前任务相关的历史记录；
5. 创建或更新本次任务记录后再修改项目文件。

`agent/record/` 不会因为目录存在而被自动完整加载，因此必须主动按需读取。
